# Migrating from the flat templates to 1.0

The flat include paths (`security/*.yml`, `build/*.yml`, `terraform/*.yml`,
`promote/*.yml`, `test/smoke-test.yml`, `docs/wiki-sync.yml`,
`pipelines/devsecops.yml`) are removed in 1.0.0. There is no deprecation
window: on the tag that carries this guide, none of those files exists, and an
`include:` naming one fails pipeline creation with `Local file ... does not
exist`.

Nothing breaks on the day 1.0.0 merges, because every consumer pins a ref. A
consumer keeps working on the ref it has pinned until it moves, and it moves to
1.0.0 and the new include in one change. That is what this guide is for.

Only some of 1.0.0 is integration-tested; `.ci/catalog.yml` records which.
Migrate one project at a time, on a branch, and read the pipeline that GitLab
actually creates before merging.

The removed-path table below is a superset: 0.x was not identical everywhere it
was deployed, so a path listed here may never have existed in your copy. Match
on the includes you actually have.

## What changes for every consumer

**Every job is renamed.** A component emits `<instance>:<component-name>`, so
`gitleaks` becomes `api:security-secrets-gitleaks` and `buildkit-build` becomes
`api:container-build-buildkit`. Anything outside the pipeline that names a job
— a required status check on a protected branch, a dashboard, a script that
polls the jobs API — must be updated in the same change. This repository does
not update them.

**A consumer stops declaring jobs.** The composition owns `stages:`,
`workflow:`, the `needs:` graph and the source rules. A consumer supplies
inputs. If you are still writing `rules: - when: never` to switch a job off,
you are on the wrong composition: pick the one that emits only what you want.

**A consumer's own `needs:` replaces the template's; GitLab never merges
them.** That is why producers are now explicit inputs (`build-job`,
`plan-job`, `sbom-job`, `sarif-report-jobs`) instead of hard-coded `needs:`
entries you were expected not to override.

**Artifacts move** to `.ci-artifacts/<instance>/<component-name>/`.

**A component job no longer inherits your `default:` block.** Every component
declares `inherit: default: [tags, timeout, interruptible, retry, id_tokens]`,
so a global `image`, `before_script`, `after_script`, `cache`, `services`,
`artifacts` or `hooks` reaches your own jobs and stops at the component's. That
is deliberate: a component runs the image it pins and the shell it ships. One
consumer lost a `quality-sonarqube` job to a global pip cache being restored
into a container that runs as uid 1000. If you relied on a global
`before_script` to prepare a component job, move that setup into the
component's inputs or into a job of your own that the component depends on.
Your `default: tags:` and `default: timeout:` still apply.

**`ref:` must be a full commit SHA or a protected release tag.** Consumers
commonly pinned `main` before 1.0.0. `.ci/estate.yml` now records
`shared_ci.approved_ref`; pin that, or a commit SHA you reviewed.

**Terraform: `.terraform.lock.hcl` must carry the runner's platform.** The
terraform components run `terraform init -lockfile=readonly`, so the lock file
is authority rather than something init may rewrite. A lock file generated on a
workstation records the `h1:` hash for that workstation's platform only, and the
runners are `linux_amd64`, so `terraform-validate`, `terraform-plan` and
`terraform-apply` fail with:

```
the cached package for registry.terraform.io/... does not match any of the
checksums recorded in the dependency lock file
```

The fix is one command per root module, committed with the lock file:

```bash
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
```

It adds one `h1:` line per provider and changes no version, so it is not a
provider upgrade and needs no plan review of its own. Two Terraform consumers
hit this on their first 1.0.0 release-candidate pipeline, so expect it. A module
repository is unaffected: it commits no lock file, which is
what `lockfile-mode: module` exists for.

## Three worked consumer shapes

Three real migrations, with the consumers described by what they do rather than
named. They are here because the awkward parts are the same everywhere: a
composition you cannot merge with another, a component whose defaults differ
from what you pin today, and bespoke jobs that no component replaces.

### A Go service building one image — the devsecops consumer

Today: one include of `/pipelines/devsecops.yml`, four builders of which two
are disabled with `rules: - when: never`, a Helm chart published on every
default-branch push, `TRIVY_EXIT_CODE: "0"` making the image scan advisory
while `cosign-sign` treats it as a gate, and three bespoke jobs (`go-test`,
`helm-lint`, `helm-template-kubeconform`).

The container half becomes:

```yaml
include:
  - project: 'platform/gitlab-ci-templates'
    ref: '<reviewed SHA>'
    file: '/pipelines/container-buildkit.yml'
    inputs:
      instance: demo-app
      image-repository: 'registry.example.com/dev/platform/demo-app'
      dockerfile: 'Dockerfile'
      semgrep-rules: 'ci/semgrep-rules.yml'
      lockfiles: 'go.sum'
      vigil: 'true'
      vigil-url: '<the project VIGIL_URL value>'
```

`ko-build` and `jib-build` disappear because this composition has one builder.
`trivy-image`, `syft-sbom`, `cosign-sign`, `vigil-notify` and `promote-prod`
become `demo-app:security-image-trivy`, `demo-app:security-sbom-syft`,
`demo-app:container-sign-attest-cosign`, `demo-app:security-sync-vigil` and
`demo-app:container-promote-harbor`. Two behaviour changes land here and are the
point of the migration: the image scan gates for real, and promotion is manual
on a protected tag.

**Unresolved: the chart.** Section 6.2 forbids merging two root compositions,
and `helm-chart` is a root composition with its own `workflow:` and `stages:`.
There is no parent-child composition in 1.0.0-rc.1, and the flat Helm template
that used to sit beside the container chain is removed. Until a parent-child
composition exists, publish the chart from its own project with
`/pipelines/helm-chart.yml`, or keep this project on its current pinned ref
until it can. Do not include both compositions in one `.gitlab-ci.yml`.

`go-test` stays bespoke: no `quality-test-*` component exists. Name it in
`sarif-report-jobs` if SonarQube must read its coverage.

### A configuration-management repository — SonarQube plus CD triggers

Today: three includes (`/security/sonarqube.yml`,
`/promote/jenkins-trigger.yml`, `/promote/semaphore-trigger.yml`), 25 jobs, of
which 23 are bespoke. `/promote/semaphore-trigger.yml` is dead — no job
extends it — and should simply be dropped.

`sonarqube` becomes:

```yaml
include:
  - project: 'platform/gitlab-ci-templates'
    ref: '<reviewed SHA>'
    file: '/templates/quality-sonarqube/template.yml'
    inputs:
      instance: infrastructure
      stage: verify
      sources: 'ansible'
      exclusions: '<the existing SONAR_EXCLUSIONS value>'
      sarif-report-jobs:
        - job: 'yaml_lint'
        - job: 'json_lint'
```

`sarif-report-jobs` is required and has no default. This repository produces no
SARIF, so it names the jobs the analysis must still follow. The old template
degraded silently to "SonarQube's own analysis only" when a consumer replaced
its `needs:`; now a job named here that the pipeline does not create fails
pipeline creation.

`policy-mode` defaults to `advisory`, which matches the `allow_failure: true`
this job has today. The gate result is now always waited on and read back,
which is the change: a green pipeline used to mean the upload succeeded, not
that the gate passed.

`trigger_jenkins_seed` becomes `/templates/release-trigger-jenkins/template.yml`
with `instance`, `job-path: '_seed-all-dsl-jobs'` and its `changes:` rule
passed through `run-rules`. Keep the rule exactly as it is: the component
default never fires on a merge request, and nothing about this migration should
make a live CD trigger more automatic.

Ansible linting can move to `/templates/ansible-lint/template.yml` and
`/templates/ansible-syntax/template.yml`, but **pass `execution-image`
explicitly** if you pin a different version today: the components default to a
public ansible-lint 26.4.0 image. Adopting the default is a rule-set change and
needs its own green run, not a side effect of a migration.

The other 20 jobs stay bespoke. No component covers `yamllint`, `djlint`,
`shellcheck`, a JSON syntax sweep, `detect-secrets` with an audited baseline,
`pytest`, Molecule, the Rundeck trigger, or the fleet OS SBOM run. Do not
force-migrate `secrets_scan` to `security-secrets-gitleaks`: the baseline
encodes roughly 200 audited false positives and the job is blocking.

### A documentation repository — SonarQube plus wiki sync

Today: two includes (`/security/sonarqube.yml`, `/docs/wiki-sync.yml`), seven
jobs, five of them bespoke.

`wiki` becomes:

```yaml
include:
  - project: 'platform/gitlab-ci-templates'
    ref: '<reviewed SHA>'
    file: '/templates/docs-wiki-sync/template.yml'
    inputs:
      instance: docs
      working-directory: 'docs'
```

The component, not the composition, because this project has its own checks and
`/pipelines/docs-wiki.yml` owns `workflow:` and `stages:`.

Two things this project must do itself:

- `WIKI_SYNC_REF` and `WIKI_SYNC_PROJECT` are gone. The sync runtime is
  vendored into the component, so the `ref:` you pin is the code that runs.
  That closes the hole where a pinned include still fetched `main` scripts at
  job time.
- `.not_for_wiki_sync` is gone. It was a template fragment that suppressed
  every job in the consumer's pipeline on trigger and schedule sources, and it
  cost one consumer its scheduled pipelines. If `markdownlint`, `links`,
  `sonarqube` and `kb-sync` should not run on a wiki-triggered pipeline,
  declare that in this project's own rules:

  ```yaml
  rules:
    - if: '$CI_PIPELINE_SOURCE == "trigger"'
      when: never
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
      when: never
    - when: on_success
  ```

`sonarqube` migrates as in the previous shape. `markdownlint`, `links`, `kb-sync`
and the parked Pages build stay bespoke; no `docs-lint-*`, `docs-links-*`,
`docs-sync-*` or `docs-publish-*` component exists.

## What has no replacement yet

These were surveyed across the consuming projects and deliberately not built in
1.0.0, because each is used by exactly one repository — the D-scope rule builds
a component only for a capability two or more repositories share. They stay
bespoke, and a repository keeping them is not out of compliance:

Go/Python test runners producing coverage, Molecule role tests, `detect-secrets`
with an audited baseline, `yamllint` / `djlint` / `shellcheck` / JSON syntax
sweeps, the Rundeck trigger, fleet-wide Ansible SBOM collection, markdown lint,
link checking, Open WebUI knowledge-base sync, and GitLab Pages publishing.

## Order of work

1.0.0 releases the components and compositions and deletes every path in the
table above in the same version. The order that makes that safe is the order
the release follows:

1. The tag is cut on the branch that holds both halves, so one ref carries the
   new layout and the guide for moving to it.
2. Each consumer moves to that tag and its new include, on a branch, with the
   pipeline it creates read before merging.
3. Only then does the release become the default anything pins.

A consumer that has not moved yet is not broken: it stays on the ref it pinned,
where its old include still resolves. It breaks only if it repoints to 1.0.0
without changing its `include:`, which is why nothing repoints a consumer's ref
for it.
